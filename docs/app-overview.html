🗺 Application Overview

The Field Service Schedule Board is a web application used by dispatchers and service managers to view, schedule, and manage field technician bookings synced from Microsoft Dynamics 365 Field Service (CRM). It provides a live calendar view of every technician's work across all regions, supports drag-and-drop rescheduling, and writes changes back to Dynamics in real time.

ℹ️
Access is controlled by the Admin Console. All users must sign in with their Microsoft work account (Entra ID). The Admin Console maps each user to either Read-Only (Viewer) or Read/Write (Editor).

Who uses this app

  • Dispatchers (Editors) — schedule, reschedule, create blocks & placeholders, add notes, sync to CRM
  • Managers / Viewers — read-only board view, utilization reporting, work order detail lookup

What it does

  • Live calendar board for all technicians across all regions
  • Drag-and-drop booking rescheduling (queued or direct CRM write)
  • Schedule blocks: Drive Time, PTO, Custom
  • Placeholder jobs for pre-sales or unconfirmed work
  • Utilization tracking and reporting

✨ Feature Reference

Schedule Board (Main View)

All Users

Board Views

Week and month calendar views. Toggle between by-region (technicians grouped under their service territory) and stacked single-tech view (focused drill-down for one technician). Navigation arrows move forward/back by week or month.

All Users

Bookings Display

CRM bookings shown as colour-coded chips on each technician's row. Each chip shows work order number, customer, city/state, and duration. Conflict detection highlights overlapping bookings in red.

Editor Only

Drag & Drop Reschedule

Drag a booking chip to a new technician/day cell to stage a reschedule. Drop re-assigns the technician and date. Changes are queued as pending write-backs until synced, or saved directly to CRM via the direct-save path.

Editor Only

Schedule Blocks

Create Drive Time, PTO, or Custom blocks for any technician on any date. Blocks carry optional title, notes, duration, and colour. Blocks are stored locally in PostgreSQL, not in Dynamics.

Editor Only

Placeholder Jobs

Pre-schedule unconfirmed or prospective jobs on the board. Store customer name, city/state, service location, notes, colour, and status (PO received, credit hold, etc.). Optionally link to a service location record for full detail.

All Users

Unscheduled Jobs Panel

Side panel listing all work orders with no active booking. Each unscheduled job shows customer, location, duration, due date, and best-fit technician suggestions ranked by nearby job density. Editors can drag these onto the board to create a booking.

All Users

Search

Global search across scheduled, unscheduled, and potential (placeholder) jobs by work order number or customer name. Results navigate to the relevant date on the board.

All Users

Work Order Detail

Click any booking chip to open a detail drawer showing full work order info: customer, contact, service address, equipment list (with calibration dates), products, services, priority, and booking history.

Editor Only

Booking Notes

Attach a free-text dispatcher note to any CRM booking. Notes are stored locally (PostgreSQL) and shown on the chip tooltip. Notes persist across rescheduling.

All Users

Resource Utilization

Panel showing each technician's booked hours vs capacity (default 40 h/week). Breakdowns by region with per-technician percentages. Includes placeholder-job minutes separately. Supports week, month, and quarter views.

All Users

Writeback Queue Status

View page (/writebacks) showing all pending, synced, and errored write-backs. Each entry shows booking ID, technician, times, status, and any error message from Dynamics.

Admin / Editor

CRM Sync & Mirror

Manual trigger to process the writeback queue and push changes to Dynamics. Admin routes to sync the CRM mirror database and backfill historical data from Dynamics. Sync status is displayed in the writeback list.

Reporting

All Users

Completed Not Approved

Service orders that have reached "Completed" status but have not yet been approved. Filterable by region, year, and month.

All Users

Approved Not Invoiced

Service orders approved but not yet exported to the invoicing system (AX). Filterable by region.

All Users

Weekly Approved

Volume of approved service orders grouped by approver and week. Filterable by region, approver, year, and month. Helps track throughput per approval workflow.

🗄 Database Schema

Most CRM mirror tables are created out-of-band (not via Drizzle). Running drizzle-kit push without care will drop undeclared tables. Only the four tables below are managed by Drizzle — everything else in the CRM mirror must be managed via SQL scripts.

🔒 Security & Permissions

Authentication Flow

Authentication uses Microsoft Entra ID (Azure AD) via OAuth 2.0 / OIDC. The MSAL Confidential Client handles the authorization code exchange server-side — no tokens are ever sent to the browser. After a successful code exchange, the server calls the Admin Console to verify that the user is explicitly permitted to access this application.

🛡 Session Security

  • Sessions stored in PostgreSQL (connect-pg-simple), not in-memory
  • Session ID regenerated after every successful login (session fixation prevention)
  • HttpOnly cookie — inaccessible to JavaScript
  • Secure flag set automatically in production
  • SameSite: Lax in production; None in development (required for Replit iframe preview)
  • Rolling 30-day expiry
  • SESSION_SECRET required in production (app refuses to start without it)

🔀 Open Redirect Prevention

The returnTo parameter on the login route is sanitised by sanitizeReturnTo():

  • Must be a same-origin absolute path (starts with /)
  • Rejected if it starts with // (protocol-relative) or /\ (Windows path abuse)
  • External URLs are silently discarded; fallback is /

Role Model

The application has exactly two session roles. These are assigned at login and cannot change mid-session.

✏️ Editor (Read/Write)

Assigned when Admin Console returns a role string containing read/write or read / write (case-insensitive). Can perform all read operations plus:

  • Create / update / delete schedule blocks
  • Create / update / delete placeholder jobs
  • Queue or directly save CRM booking changes
  • Trigger write-back sync
  • Write and delete booking notes
  • Trigger CRM mirror sync and backfill (admin routes)

👁 Viewer (Read-Only)

Assigned when Admin Console returns an allowed user with a non-editor role. Can:

  • View the schedule board (all views and date ranges)
  • View work order details
  • View utilization reports
  • View service location details
  • View write-back queue status
  • View booking notes
  • Search across all jobs

All write UI controls (Add Block buttons, drag handles, edit/delete on chips, schedule unscheduled panel) are hidden entirely in the frontend. Any attempt to call a write API endpoint is rejected with HTTP 403 by the server regardless.

Admin Console Fallback

If the Admin Console is unreachable or returns a malformed response at login time, the server falls back to the app.app_user table in the FS database. A user with role = 'editor' or role = 'admin' in that table gets editor access; all other active users get viewer access; inactive users are denied (401).

✅
Defence in depth: Write operations are blocked at both layers. The API middleware rejects 403 for any viewer attempting a write, regardless of what the frontend shows. There is no path for a viewer to perform a write operation by manipulating the UI.

🔗 External Integrations

🔵 Microsoft Entra ID

Purpose: User authentication (OAuth 2.0 / OIDC)

Flow: Authorization Code with PKCE (server-side MSAL Confidential Client)

Endpoints:

  • Authority: https://login.microsoftonline.com/{TENANT_ID}
  • Logout: /oauth2/v2.0/logout
  • Redirect URI: {APP_URL}/api/auth/callback

Env vars: ENTRA_TENANT_ID, ENTRA_CLIENT_ID, ENTRA_CLIENT_SECRET, ENTRA_REDIRECT_URI

🛡 Admin Console

Purpose: Per-user app entitlement (allowed + role)

Called on: Every login. Not called on API requests.

Endpoint: GET {ADMIN_CONSOLE_URL}/api/access-check

Params: entraObjectId, app=Field Service Calendar

Headers: X-API-Key: {ADMIN_CONSOLE_API_KEY}

Response: { allowed: boolean, reason: string|null, roles: string[] }

Env vars: ADMIN_CONSOLE_URL, ADMIN_CONSOLE_API_KEY

🟠 Microsoft Dynamics 365 / Dataverse

Purpose: Source of truth for work orders and bookings. Write target for reschedules.

Access: Two paths:

  • CRM Mirror DB — PostgreSQL replica of Dynamics data, synced periodically. Used for all read queries (fast, no Dataverse throttling).
  • Dataverse REST API — used for write-backs only (PATCH/POST to msdyn_resourcebookings)

Env vars: D365CRM_DATABASE_URL, DATAVERSE_ENV_URL, DATAVERSE_TENANT_ID, DATAVERSE_CLIENT_ID, DATAVERSE_CLIENT_SECRET

Shared API Client Library

@workspace/api-client-react is a generated TypeScript library created from the OpenAPI specification via Orval. It provides:

  • All TypeScript request/response interfaces (e.g. ScheduleBlock, PlaceholderJob, WbWorkOrder)
  • React Query hooks for every endpoint (e.g. useGetWbScheduleBoard(), useCreateWbScheduleBlock())
  • A configurable customFetch layer supporting base URL, bearer token injection, and a global 401 callback
  • Typed error classes: ApiError and ResponseParseError

The library is distributed as a pre-built dist (TypeScript declaration files + JS). To regenerate after API schema changes, run the Orval codegen workflow in lib/api-client-react/.

⚠️
The generated dist files (lib/api-client-react/dist/) must be rebuilt and committed whenever the OpenAPI spec changes. The frontend's TypeScript build reads the dist declarations, not the source. Out-of-date dist files will cause missing-export type errors at build time.

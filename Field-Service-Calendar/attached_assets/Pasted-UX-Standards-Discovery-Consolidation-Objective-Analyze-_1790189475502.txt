UX Standards Discovery & Consolidation
Objective
Analyze the current application codebase and identify the UX design patterns, conventions, components, interaction behaviors, and visual standards that have been implemented.
The goal is not to redesign the application.
The goal is to extract and document the UX decisions that already exist so they can be compared with UX standards from other applications and ultimately consolidated into a reusable enterprise UX standard.
The resulting Markdown document will become the source of truth for a future shared TypeScript UX foundation used by new applications.

1. Analyze Before Documenting
Inspect the application comprehensively before producing the UX Standards document.
Review, where applicable:
	• React components
	• TypeScript files
	• CSS
	• Tailwind configuration
	• theme files
	• design tokens
	• shared components
	• layouts
	• navigation
	• forms
	• tables
	• dialogs/modals
	• buttons
	• cards
	• notifications
	• status indicators
	• validation
	• loading states
	• error states
	• empty states
	• responsive behavior
	• accessibility implementation
	• icons
	• typography
	• spacing
	• colors
	• borders
	• shadows
	• hover/focus/disabled states
	• page-level layouts
	• application shell
	• header
	• sidebar
	• breadcrumbs
	• search
	• filters
	• pagination
	• sorting
	• data entry
	• confirmation patterns
Do not infer a standard merely because a framework or library supports it.
Document what is actually implemented.

2. Separate Standards From Application-Specific Choices
For every UX pattern, determine whether it is:
STANDARD
A reusable UX convention that should potentially apply across applications.
APPLICATION-SPECIFIC
A decision that is appropriate to this application’s business process but should not automatically become an enterprise standard.
CANDIDATE STANDARD
A useful pattern that appears intentional and reusable, but should be reviewed before becoming part of the enterprise UX standard.
INCONSISTENT
A pattern that conflicts with another implementation or appears to have been implemented differently in different places.
UNKNOWN
The code does not provide enough evidence to determine the intended standard.
Do not convert application-specific behavior into a corporate UX standard simply because it exists.

4. Capture Actual Evidence
For every significant UX standard, provide evidence from the application.
Use this format:

Page Header	Title + subtitle	PageHeader.tsx	Standard

Reference the actual component, file, CSS class, token, or implementation where possible.

7. Identify UX Inconsistencies
Look specifically for cases where the same interaction is implemented differently.
Examples:
	• Two different primary button styles
	• Different meanings for the same status color
	• Different form label placement
	• Different modal behavior
	• Different table density
	• Different spacing
	• Different error-message conventions
	• Different navigation patterns
For each inconsistency document:
	1. Pattern
	2. Implementation A
	3. Implementation B
	4. Likely intended standard
	5. Recommendation for human review
Do not automatically choose a winner.

8. Identify UX Decisions That Should NOT Become Standards
Explicitly identify application-specific patterns that should remain local to the application.
Examples:
	• specialized workflow layouts
	• domain-specific terminology
	• unusual data-entry sequences
	• specialized production scheduling controls
	• application-specific dashboards
	• unique business-process states
This is important.
The purpose of the standard is to create consistency without forcing every application into the same UX model.

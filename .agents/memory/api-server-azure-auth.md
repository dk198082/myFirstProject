---
name: Azure auth in api-server
description: How Entra/Azure login is wired into the api-server and why existing routes are not gated.
---

The api-server has Entra (Azure AD) login via MSAL authorization-code flow, mounted under `/api` (so `/api/login`, `/api/auth/callback`, `/api/me`, `/api/logout`). Sessions are stored in Postgres (`DATABASE_URL` / `localPool`) via connect-pg-simple; `requireLogin` / `requireRole` middleware exist.

**Decision:** Existing business routes (writeback, technicians, workOrders, dashboard, schedule board, etc.) are intentionally NOT yet wrapped with auth middleware — this remains true even though dynamics-write-back now has a login gate.
**Why:** field-service-schedule-board AND dynamics-write-back both call the SAME shared `/api/wb/*` endpoints, but field-service-schedule-board has no login. Gating those shared routes server-side would 401 the schedule board. So per-app login must be enforced client-side, not by gating the shared routes.
**How to apply:** Before adding `requireLogin`/`requireRole` to existing routers, confirm EVERY frontend that calls that route performs login, or you will break the ones that don't. Azure app registration must have the redirect URI registered and users seeded into `app.app_user`.

**Current state:** dynamics-write-back has a client-side Entra login gate (AuthProvider/useAuth + LoginGate in its `src`) that calls `/api/me` and renders a "Sign in with Microsoft" screen when 401. It's a UX gate only, NOT a real authz boundary (shared wb routes stay open). If real authorization is needed later, protect only the mutating write-back routes and give the schedule board its own login too.

**returnTo:** `/api/login?returnTo=<relative path>` is supported — `sanitizeReturnTo` (in routes/auth.ts) only accepts same-origin paths (rejects `//`, `/\`, absolute/non-string) and callback redirects there instead of hardcoded `/`. Needed because path-based apps (e.g. `/dynamics-write-back/`) must land back in their own app after login.

**Redirect URI MUST include /api.** The Azure app registration redirect URI must be `https://<domain>/api/auth/callback` (WITH `/api`). The auth router is mounted at `app.use("/api", router)`. A `/auth/callback` (no `/api`) URI can NEVER work: the shared proxy only routes `/api/*` to the api-server, so root `/auth/callback` hits a frontend and the token exchange never runs. Register BOTH the prod domain and the current dev `.replit.dev` domain (dev URL changes over time). AADSTS50011 echoes the *request's* redirect_uri, not the registered one.

**Deployment-scoped env overrides are INVISIBLE to workspace `viewEnvVars` and survive every rebuild.** A published Replit deployment keeps its own copy of secrets/env, editable in the Deploy pane, NOT shown by `viewEnvVars` (which only sees workspace/dev). Symptom seen here: prod's `msal.js.node` authorize request kept sending `.../auth/callback` (no `/api`) even after republishing and even though a fresh build of current source provably emits `/api/auth/callback` and dev sent `/api`. Root cause: a leftover `ENTRA_REDIRECT_URI=https://work-order-hub.replit.app/auth/callback` (from the original standalone server) set in the *deployment* env, overriding the code default. **Debugging rule:** if prod behaves differently from dev for an env-driven value and a fresh build can't reproduce it, suspect a deployment-scoped env/secret override — don't keep rebuilding. **Fix applied:** `resolveRedirectUri()` in lib/auth.ts now takes only the ORIGIN from `ENTRA_REDIRECT_URI` and always forces the `/api/auth/callback` path, so a stale/legacy override can't break login. `lib/auth.ts` also logs the resolved `redirectUri` at startup — check deployment logs to confirm what prod actually uses.

**Authorization requires a row in `app.app_user` (schema `app`, not public).** The callback (routes/auth.ts) exchanges the code, then looks up `app.app_user WHERE entra_oid=$1 AND is_active=true`; 0 rows → 403 "authenticated but not authorized". So a user only gets in if their Entra object id (oid) is seeded there. The table was created out-of-band via psql and was empty in BOTH dev and prod, so login never completed end-to-end until seeded. In production the table was also MISSING entirely → the callback threw `relation "app.app_user" does not exist` (42P01) which the catch turned into a generic 500 "Login failed". `app_user` is now declared in Drizzle (`lib/db/src/schema/appUser.ts`, `pgSchema("app")`). **IMPORTANT — Publish did NOT create it in prod.** Re-publishing after declaring it left prod still throwing 42P01 — the Replit Publish schema migration did not create the custom `app` schema table (custom non-`public` pgSchema and/or the publish migrate step is inert here, consistent with the `sessions`-table gotcha). So the `app` schema + `app_user` table had to be created by running CREATE SCHEMA/CREATE TABLE SQL **directly against the production DB** (user runs it; prod DB is read-only to the agent), same as the sessions table. **Seeding:** to find a user's oid, have them sign in once → the callback logs `{entraOid,email,displayName}` on the not-authorized (403) branch → `INSERT INTO app.app_user (entra_oid,email,display_name,role) VALUES (...)`. Seed BOTH dev (agent via executeSql) and prod (user runs SQL). `role` is display-only (no CHECK, not used for gating). First seeded user: Sanjay K Pathak (admin).

**CONSOLIDATION (chosen): dev overridden onto the prod app registration `21d8a84f-e59e-48b7-a27f-fc2f29933058`.** The auth code reads `ENTRA_CLIENT_ID ?? CLIENT_ID` (and same for TENANT/SECRET), so ENTRA_* wins over the bare names. Dev's bare `CLIENT_ID` was `ce7585ab…` (a separate app); to switch dev without touching prod, set `ENTRA_CLIENT_ID=21d8a84f…` as a **development-scoped env var** (`setEnvVars`) and set `ENTRA_CLIENT_SECRET` (a NEW client secret generated on app 21d8a84f) as a **global secret** (`requestEnvVar`). Tenant is the SAME for both apps (`9b2f8eb8-7925-4337-91c7-19c1010714c0`), so no tenant override needed — leave bare `TENANT_ID`. Prod is unaffected: it has no `ENTRA_CLIENT_ID`, so it keeps using bare `CLIENT_ID` (=21d8a84f), and the global `ENTRA_CLIENT_SECRET` is a valid secret for that same app. Verify with `curl -sD- localhost:80/api/login | grep -i location` — the `client_id=` must be 21d8a84f. NOTE: the bare `CLIENT_ID`/`TENANT_ID`/`CLIENT_SECRET` are present in the api-server runtime env (visible via a node shell check) but do NOT appear in `viewEnvVars` output — they're injected outside the workspace-secrets pane, which is why ENTRA_* overrides (rather than editing the bare vars) is the clean lever.

**DEV and PROD use DIFFERENT Azure app registrations (different client_id).** The shared api-server's `CLIENT_ID` differs between the workspace/dev env and the deployment/prod env (deployment secrets are separate — see the deployment-scoped-env note). Observed: dev's authorize request uses application/client id `ce7585ab-1157-4757-b9cf-60598650c8f8`; prod uses a different one (historically noted `21d8a84f-e59e-48b7-a27f-fc2f29933058`). Consequence: the callback redirect URI must be registered **on the specific app registration that environment uses** — registering the prod domain on the prod app does nothing for dev. Since BOTH frontends (dynamics-write-back and field-service-schedule-board) hit the same `/api/login`, they share the same client_id per environment, so fixing one fixes both in that env. AADSTS50011 names the exact `application '<clientId>'` in the error — use that to know which registration to edit. Dev `.replit.dev` domains are ephemeral and change over time, so each new dev domain's `/api/auth/callback` must be re-added to the dev app registration (Azure Web platform redirect URIs; no wildcard support).

**Login page can't be iframed.** login.microsoftonline.com sends X-Frame-Options/frame-ancestors, so signing in inside an embedded view (Replit preview/canvas iframe) shows "refused to connect". useAuth.login() detects `window.top !== window.self` and opens OAuth in a new top-level tab (falls back to top navigation). Logout hits the same limit (redirects to Entra logout) — best tested from the app opened directly in its own tab. In production (opened directly, not framed) both work normally.
